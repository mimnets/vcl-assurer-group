### Decisions taken in the task (from the installed source)

1. **Trailing-slash 301 is project middleware, not a redirect record.** The redirect module cannot
   match `/x/` (its slug pattern forbids a trailing slash) and core's own redirect is a 302 that
   drops the query string and runs after the redirect middleware, so `/old/` would take two hops.
   `assurer-seo` registers a middleware `before: '@apostrophecms/redirect'` that hands the
   slash-less URL to the redirect module; a legacy record for `/old` therefore answers `/old/` in
   one hop. If nothing matches, the module's `noMatch` event (an official extension point) sends
   301 to `/x`. Nothing else is reimplemented.
2. **Legacy redirects are ordinary, editor-editable redirect records.** The seed task adds missing
   records only, links targets as page relationships (they follow slug changes), never edits or
   removes a record (an edited one is reported as "changed" and left alone), skips a redirect whose
   target page is not published, and refuses one that would hide a published page. `--strict`
   fails while any is missing (used in CI).
3. **No content migration.** The new fields are optional with empty defaults and the seo package
   ships no migrations; no existing document needs a change (ADR-0002). The redirect package's own
   startup migrations (`unlocalized`, `addTargetLocale`, `caseInsensitive`, on an empty
   collection) were run first on a copy of the local development database: they succeeded, and a
   second run did nothing. The development database was backed up first (outside the repository).

  archived first (runbook §3).

  **D-CONTENT-13**.

  valid schema.org usage; not changed.
- Structured-data types Article/BlogPosting fall back to the editor's name as author; documented in
  the runbook; relevant only when news is built (D-CONTENT-6).

- One H1 per page in templates (SEO plan §4) belongs to CA-4.
